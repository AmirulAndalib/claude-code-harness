Claude Code Harness (略称 CCH) は、AI コーディングツールに「計画 → 実装 → 検証 → レビュー → リリース」を決まった手順で回させ、危ない操作は実行前に止め、最後に人が Yes / No を言うだけで済むようにする追加パーツ (プラグイン) です。AI を賢くする道具ではありません。AI の周りに手順と柵を作る道具です。

やさしく言うと
AI にプログラムを書かせるのは、もう普通にできます。問題は「任せっぱなしにすると、途中で話がずれる、テストを飛ばす、危ないコマンドを打つ、できてないのに『できました』と言う」ことです。CCH はこの 4 つを仕組みで防ぎます。人は途中で見張らなくてよくなり、最後に「これで出していいか」を判断するだけになります。

01 — Why

何を解決するか

AI に任せた開発は、放っておくと 4 か所で崩れます。CCH はそれぞれを「お願い」ではなく「仕組み」で押さえます。

🗂️
計画が消える
計画はチャットに流れて消える。あとで「何を頼んだっけ」になる
spec.md と Plans.md にファイルとして残る。作業ごとに todo / 進行中 / 完了 の印が付く
🧪
テストが飛ぶ
締切が近いと省略される。「テストは後で」が常態化
「テスト必須」の作業では、テストを先に書かないと実装ファイルへの書き込みが止まる
🛑
危ない操作
実行されてから気づく。消えたファイルは戻らない
実行前に判定。床 5 つは絶対に止まる。ほかは「止める / 確認 / 警告」を事前に決められる
📋
「できました」が自己申告
AI の言葉を信じるしかない。数えると抜けていることがある
テストログや録画などの実行記録から機械が引用。検証できなかった項目は「未検証」と表示され、出荷推奨にならない
02 — Quick start

30 秒で導入

Claude Code を開いて、次を 1 行ずつ打ちます。

claude
› /plugin marketplace add Chachamaru127/claude-code-harness
› /plugin install claude-code-harness@claude-code-harness-marketplace
› /harness-setup
# そのあと、小さめの依頼を 1 つ渡す
› /harness-plan README の導入手順をわかりやすくして
✔ spec.md と Plans.md の下書きができました。承認するか、直してください。

CCH が仕様書 (spec.md) と作業一覧 (Plans.md) の下書きを作ります。あなたの仕事は計画を書くことではありません。出てきた計画を承認するか、直すことです。あとは /harness-work で実装、/harness-review で審査、判断画面で Yes / No です。

Claude Code 以外 (Codex CLI / Cursor / Grok) で使う

同じ手順と同じ柵が効きます。入れ方はツールごとに少し違います (Codex CLI: scripts/setup-codex.sh --user、Cursor: scripts/setup-cursor.sh、Grok: scripts/setup-grok.sh)。CCH は 1 つの判定エンジンが 4 つのツールに同じ判定を返す作りです (コピーではなく振り分け)。

03 — The loop

覚えるのは 5 つの動詞だけ

全部 /harness- で始まります。各段階は、次の段階が必要とする材料を残して終わります。

📝
計画する
/harness-plan
やりたいことを伝えると、仕様書と作業一覧を書く。範囲、合格条件、順番、わからない点、止まる条件が全部入る
人がやること: 承認するか直す。自分で計画を書く必要はない
🔨
実装する
/harness-work
承認された作業を 1 つ、または全部 (all) 実装する。テスト必須の作業ではテストを先に書く
人がやること: 待つ。途中確認は原則なし
🔍
審査する
/harness-review
実装した AI とは別の頭が結果を審査。大きな問題があれば完了扱いにしない。別会社の AI (Codex) の第二意見も並走できる
人がやること: 待つ
🧭
突き合わせる
/harness-sync
計画と実際にできたものを比べ、ずれを報告する
人がやること: ずれの報告を読む
🚀
出荷する
/harness-release
検証済みの証拠だけを使って、変更履歴、タグ、公開までを一括で行う
人がやること: 1 回だけ「出していいか」に Yes / No
🖥️
判断画面 (3 面)
Plan Brief / Progress / Acceptance
コードを読まずに判断するための 1 画面 HTML。計画確定時、作業中、出荷前の 3 場面でそれぞれ自動生成される。スマホでも見られる
人がやること: 見て Yes / No
04 — Safety layer

すべての操作は、実行前に判定される

ここがプロンプトの雛形と CCH の違いです。AI が何か操作をするたびに、Go 言語で書かれた小さな判定プログラムが実行前に通します。ファイルの差分を後から見ても「ネットに何か送った」「ファイルを消した」は分からないので、実行前に止めるしかない、という考えです。

床 (runtime floor)
5 categories / overridable: NO
課金、外部へのデータ送信、秘密情報 (パスワード等) の読み取り、本番環境への配置、作業場所の外のファイル削除。設定や許可モードでは外せません。AI が自律で走っている最中に「まあいいか」で突破できないよう、独立した経路に置かれ、切るスイッチがありません。
ガードレール (R01〜R15)
15 rules / deny · confirm · warn
main への直接 push、保護されたファイルへの書き込み、履歴の書き換え、危険な削除コマンドなど。それぞれ「止める / 確認する / 警告だけ」が決まっていて、プロジェクトごとに調整できます。
📅
確認は計画のときにまとめて
走っている最中に何度も「いいですか？」と聞かない。計画に必要な危険操作を先に集めて 1 回で聞く
⏳
承認には期限が付く
1 回の承認には期限、対象作業、使用回数の上限が付く。一度 Yes と言ったら永久に穴が開く、ということがない
🧾
止めた記録は全部残る
ルール番号、種類、判定がログに残る。コマンド本文は書かず、ハッシュと長さだけ (秘密情報と課金はそれすら書かない)。何に止められたかを数えられる
05 — What's new in v5.9

「AI がそう言った」ではなく「実際に実行された記録」で判断する

v5.9 で完成したのが検証チェーンです。テストの実行ログ、ブラウザ操作の録画、触ったファイルの台帳を機械が集め、判断画面に引用します。検証できなかった項目は隠さず「未検証」と表示され、出荷推奨になりません (fail-visible)。

例: 「ログイン画面のエラー表示を直して」と頼んだとき (左から右へ時間が流れる)
1
計画する
仕様書と作業一覧を AI が起草。合格条件を「テストが通る」「画面にエラー文が出る」のように機械で○×が付く形に翻訳
人: 承認 or 修正 (唯一の事前判断)
2
実装する
AI が実装。触っていいファイルの範囲を計画から読み取り、範囲外に手を出したら記録して警告 (scope leash)。危ない操作は柵が止める
人: 何もしない
3
検証して審査する
テストを実行、ブラウザ操作を録画、変更ファイルを台帳に記録。別の AI がその記録を見て審査。検証できなかった項目は「未検証」と明記
人: 何もしない
4
判断する
判断画面に実行記録から引用した証拠が並ぶ。未検証があれば「出荷推奨」にならない。人はそれを見て Yes / No
人: Yes / No (最後の判断)
🔗
検証チェーンの修理
入口 (リスクに応じたレビュー強度の自動昇格)、中間 (ブラウザ検証待ちを黙って合格にしない)、出口 (受け入れ判定は AI の再主張ではなく成果物から読む) の 3 か所を配線し直した
✍️
日本語の品質チェック
「効く」「A ではなく B」のような癖のある日本語を書いた直後に検出し、その文を丸ごと書き直し + 良い例を返す。既定 off の opt-in。辞書は空から始まり、指摘 → 承認で育てる
🎯
範囲外の見張り (scope leash)
計画に書いた範囲の外のファイルに手を出したら記録して警告する。今は警告のみ。強制的に止めるモードは、実績を見てから使う人が切り替える

数字で言うと: v5.9 の開発自体を CCH で回した実績では、24 件の作業を AI が実装し、レビュー 3 往復 (1 回目で本物の問題 4 件、2 回目で 1 件を検出) を経て合格しました。その間に人が判断したのは「計画の承認」「4 つの設計判断」「リリースしていいか」の合計 6 回でした。

07 — Who

誰のためのものか

✅
向いている人
  • 一人で開発していて、AI に実装を任せたい人
  • コードを全部は読めないが「本当にできたか」は自分で判断したい人
  • Claude Code と Codex CLI など、複数の AI ツールを行き来する人
  • 途中で何度も「いいですか？」と聞かれるのが嫌な人
⚠️
向いていない場面
  • 1 行直すだけの作業 (計画と審査の手順が重く感じる)
  • AI が間違えなくなることを期待している場合 (間違いを止める / 見つけるだけで、無くしはしない)
  • Claude Code v2.1 より古い環境

09 — FAQ

よくある質問

AI が賢くなるの？

なりません。CCH は AI の周りに手順と柵を作る道具です。だからモデルが新しくなっても、そのまま使えます。

本当に途中で聞かれなくなる？

危険操作の確認は計画のときにまとめて 1 回だけ聞きます。ただし床 5 つ (課金、外部送信、秘密情報の読み取り、本番配置、作業場所の外の削除) は設定で外せないので、そこに当たれば止まります。

「できました」をどう信じればいい？

信じなくていいように作ってあります。判断画面に並ぶのは、テストログ、録画、変更台帳などの実行記録からの引用です。検証できなかった項目は「未検証」と表示され、その状態では出荷推奨になりません。

Node.js は要る？

要りません。判定エンジンは Go 言語で書かれた単体の実行ファイルです。必要なのは Claude Code v2.1 以上と、書き込みできるリポジトリだけです。

この説明書に書いてあることは本当？

README の記述は CI で機械検査されています。書かれている部品が実際に配線されているか、作業一覧の依存関係が矛盾していないか、配布バイナリがソースから再生成できるかを確認します。「書いた」は「動く」ではない、が方針です。

10 — Glossary

この説明書に出てくる言葉

プラグイン = アプリに後から足す追加パーツ。
CCH は Claude Code のプラグインとして入れます。
spec.md / Plans.md = 仕様書と作業一覧の 2 つのファイル。
AI が書き、人が承認します。作業一覧の各行に「未着手 / 進行中 / 完了」の印が付き、AI が勝手に「完了」に書き換えることは禁止されています。
柵 (床とガードレール) = AI の操作を実行前に判定する仕組み。
床 = 絶対に越えられない 5 つ。ガードレール = 調整できる 15 本。判定は Go 言語のプログラムが行い、AI の気分では変わりません。
証拠 (evidence) = 実際に実行された記録。
テストの実行ログ、ブラウザ操作の録画、触ったファイルの台帳など。「AI がそう言った」は証拠に数えません。
fail-visible = 検証できなかったことを隠さず表示する方針。
止めはしないが、緑にもしない。判断画面に「未検証」と出て、出荷推奨になりません。
HOTL = human on the loop。人は上から眺めて最後に判断する。
対義語は HITL (human in the loop、途中で何度も人が確認する)。CCH は HOTL を目指しています。
この説明書のまとめ
CCH は「AI を賢くする道具」ではなく「AI の周りに手順と柵を作る道具」です。人の仕事は 2 か所 (計画の承認、最後の Yes / No) に絞られ、その Yes / No は AI の自己申告ではなく実行された証拠に基づきます。v5.9 でその「証拠で判断する」部分が完成しました。
正直な但し書き
  • CCH を入れても AI が間違えなくなるわけではありません。間違いを「実行前に止める」「実行後に証拠で見つける」ようになるだけです。
  • 日本語の品質チェックは既定 off です。辞書も空から始まり、使う人が指摘 → 承認して育てます。
  • 範囲外ファイルの見張り (scope leash) は今は警告のみです。強制的に止めるモードは、実績を見てから使う人が切り替えます。
  • Claude Code 本体のバージョンが上がると挙動が変わることがあります。CCH は追従を続けていますが、常に最新と一致する保証はありません。
