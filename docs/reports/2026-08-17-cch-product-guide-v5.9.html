Claude Code Harness / プロダクト説明書 (v5.9.0)

Claude Code Harness とは何か — AI に仕事を任せて、人は最後に判断するための道具

はじめて触る人、エンジニアではない人向け。専門用語は出た瞬間に言い換えます。
ひとことで: Claude Code Harness (略称 CCH) は、AI コーディングツール (Claude Code など) に「計画 → 実装 → 検証 → レビュー → リリース」を決まった手順で回させ、危ない操作は実行前に止め、最後に人が Yes/No を言うだけで済むようにする追加パーツ (プラグイン) です。AI を賢くするのではなく、AI の周りに手順と柵を作ります。
作成: 2026-08-17対象: 初見の非専門家本書は説明用の派生物であり正本ではない (正本: README.md / spec.md)
やさしく言うと
AI にプログラムを書かせるのは、もう普通にできます。問題は「任せっぱなしにすると、途中で話がずれる・テストを飛ばす・危ないコマンドを打つ・できてないのに『できました』と言う」ことです。CCH はこの 4 つを仕組みで防ぎます。人は途中で見張らなくてよくなり、最後に「これで出していいか」を判断するだけになります。
Q. 何をするもの？
AI コーディングツールの「追加パーツ」。入れると 5 つのコマンド (計画 / 実装 / レビュー / 同期 / リリース) が使えるようになり、AI が勝手に危ないことをしないよう実行前チェックが常時動きます。
Q. 誰のため？
一人で開発する人、AI に実装を任せたい人、コードを全部は読めないけど「本当にできたか」は判断したい人。エンジニアでなくても使えるように設計されています。
Q. どこで動く？
Claude Code を中心に、Codex CLI / Cursor / Grok でも同じ手順と柵が効きます (ツールが変わっても CCH は変わらない)。
Q. v5.9 で何が新しい？
「AI の自己申告」ではなく「実際に実行された記録」で検証する仕組みが完成しました。加えて AI の変な日本語をその場で直させる機能と、指摘を辞書に育てる機能が入りました。
01 — 何を使うのか

使うもの: 5 つのコマンドと 2 つの柵

CCH を入れると、AI ツールの中で次の 5 つの「合言葉 (スラッシュコマンド)」が使えます。全部 /harness- で始まります。

コマンド何が起きるか人がやること
/harness-planやりたいことを伝えると、AI が「仕様書 (spec.md)」と「作業一覧 (Plans.md)」を書きます。範囲、合格条件、順番、わからない点、止まる条件が全部入ります書かれた計画を承認するか直す。自分で計画を書く必要はない
/harness-work承認された作業を 1 つ、または全部、AI が実装します。テストが必要と書いてあれば先にテストを書きます待つ (途中確認は原則なし)
/harness-review実装した AI とは別の頭が結果を審査します。大きな問題があれば完了扱いにしません。別会社の AI (Codex) の第二意見も並走できます待つ
/harness-sync計画と実際にできたものを突き合わせ、ずれを報告しますずれの報告を読む
/harness-release検証済みの証拠だけを使って、変更履歴・タグ・公開までを一括で行います1 回だけ「出していいか」に Yes/No

2 つの柵 (安全装置)

コマンドとは別に、AI が何か操作をするたびに実行前にチェックが走ります。ファイルの差分を後から見ても「ネットに何か送った」「ファイルを消した」は分からないので、実行前に止めるしかない、という考えです。

柵 1: 床 (runtime floor) — 絶対に越えられない 5 つ
課金 / 外部へのデータ送信 / 秘密情報 (パスワード等) の読み取り / 本番環境への配置 / 作業場所の外のファイル削除。設定や許可モードでは外せません。AI が自律で走っている最中に「まあいいか」で突破できないようにするためです。
柵 2: ガードレール (R01〜R15) — 調整できる 15 本
main への直接 push、保護されたファイルへの書き込み、履歴の書き換え、危険な削除コマンドなど。それぞれ「止める / 確認する / 警告だけ」が決まっていて、プロジェクトごとに調整できます。

確認は計画のときにまとめて取ります。走っている最中に何度も「いいですか？」と聞かれない設計です。1 回の承認には期限・対象作業・使用回数の上限が付くので、一度 Yes と言ったら永久に穴が開く、ということもありません。止めた記録は全部ログに残ります。

02 — どう回るのか

つながるとこう動く: 1 つの依頼が完了するまで

例: 「ログイン画面のエラー表示を直して」と頼んだとき (左から右へ時間が流れる)
1
計画する
仕様書と作業一覧を AI が起草。合格条件を「テストが通る」「画面にエラー文が出る」のように機械で○×が付く形に翻訳
人: 承認 or 修正 (ここが唯一の事前判断)
2
実装する
AI が実装。触っていいファイルの範囲を計画から読み取り、範囲外に手を出したら記録・警告 (scope leash)。危ない操作は柵が止める
人: 何もしない
3
検証・審査する
テストを実行、ブラウザ操作を録画、変更ファイルを台帳に記録。別の AI がその記録を見て審査。検証できなかった項目は「未検証」と明記される
人: 何もしない
4
判断する
スマホでも見られる判断画面に、実行記録から引用した証拠が並ぶ。未検証があれば「出荷推奨」にならない。人はそれを見て Yes/No
人: Yes / No (ここが最後の判断)

押さえる本質: 人が判断するのは ①計画の承認 と ④最後の Yes/No の 2 回だけ。間の ②③ は AI と柵に任せます。AI に任せてよい詳細: どのテストを書くか、どのファイルを触るか、レビューの観点、変更履歴の文面。

03 — 通常との違い

比較: 素の AI ツール vs CCH を入れたとき

場面素の AI ツールだけCCH を入れたとき
計画チャットの中に流れて消える。あとで「何を頼んだっけ」になるspec.md と Plans.md にファイルとして残る。作業ごとに todo / 進行中 / 完了 の印が付く
テスト締切が近いと省略されがち。「テストは後で」が常態化作業に「テスト必須」と書いてあれば、テストを先に書かないと実装ファイルへの書き込みが止まる
危ない操作実行されてから気づく (消えたファイルは戻らない)実行前に判定。5 つの床は絶対に止まる。それ以外は「止める / 確認 / 警告」を事前に決められる
「できました」の信頼性AI の自己申告。数えると抜けていることがあるv5.9 の本丸。実行記録 (テストログ・録画・変更台帳) から機械が引用。検証できなかった項目は隠されず「未検証」表示になり、出荷推奨にならない
レビュー書いた本人 (同じ AI) が「問題ありません」と言いがち別の頭 (別セッションの AI、任意で Codex も) が実物を自分で開いて審査。基準を勝手に緩めるのは禁止
日本語の品質「効く」「A ではなく B」のような癖のある日本語がそのまま出る書いた直後に検出し「その文を丸ごと書き直し + 良い例」を返す (v5.9 新機能、既定は off で opt-in)
人の役割途中で何度も見張って口を出す (HITL: human in the loop)計画承認と最後の Yes/No だけ (HOTL: human on the loop)

数字で言うと: 今回 v5.9 の開発自体を CCH で回した実績では、24 件の作業を AI が実装し、レビュー 3 往復 (1 回目で本物の問題 4 件、2 回目で 1 件を検出) を経て合格、その間に人が判断したのは「計画の承認」「4 つの設計判断」「リリースしていいか」の合計 6 回でした。

04 — 用語

この説明書に出てくる言葉

プラグイン = アプリに後から足す追加パーツ。
CCH は Claude Code のプラグインとして入れます。入れ方は下の「使いはじめる」参照。
spec.md / Plans.md = 仕様書と作業一覧の 2 つのファイル。
AI が書き、人が承認します。作業一覧の各行に「未着手 / 進行中 / 完了」の印が付き、AI が勝手に「完了」に書き換えることは禁止されています。
柵 (床とガードレール) = AI の操作を実行前に判定する仕組み。
床 = 絶対に越えられない 5 つ。ガードレール = 調整できる 15 本。判定は Go 言語で書かれた小さなプログラムが行い、AI の気分では変わりません。
証拠 (evidence) = 実際に実行された記録。
テストの実行ログ、ブラウザ操作の録画、触ったファイルの台帳など。「AI がそう言った」は証拠に数えません。
fail-visible (未検証の可視化) = 検証できなかったことを隠さず表示する方針。
止めはしないが、緑にもしない。判断画面に「未検証」と出て、出荷推奨になりません。
HOTL = human on the loop。人は上から眺めて最後に判断する。
対義語は HITL (human in the loop、途中で何度も人が確認する)。CCH は HOTL を目指しています。
05 — 使いはじめる

最初の 3 分

Claude Code を開いて、次を順に打ちます (1 行ずつ)。

/plugin marketplace add Chachamaru127/claude-code-harness
/plugin install claude-code-harness@claude-code-harness-marketplace
/harness-setup

次に、小さな頼みごとを 1 つ渡します。

/harness-plan README の導入部分を読みやすくして

AI が仕様書と作業一覧を出してきます。読んで「これでいい」なら承認、違えば直してもらいます。ここが人の仕事です。あとは /harness-work で実装、/harness-review で審査、判断画面で Yes/No です。

Claude Code 以外 (Codex CLI / Cursor / Grok) で使う 同じ手順・同じ柵が効きます。入れ方はツールごとに少し違うので、README の「install by tool」を見てください。CCH 側は 1 つのエンジンが 3 つのツールに同じ判定を返す作りです (コピーではなく振り分け)。
この説明書のまとめ
CCH は「AI を賢くする道具」ではなく「AI の周りに手順と柵を作る道具」です。人の仕事は 2 か所 (計画の承認、最後の Yes/No) に絞られ、その Yes/No は AI の自己申告ではなく実行された証拠に基づきます。v5.9 でその「証拠で判断する」部分が完成しました。
正直な但し書き
  • CCH を入れても AI が間違えなくなるわけではありません。間違いを「実行前に止める」「実行後に証拠で見つける」ようになるだけです。
  • 日本語の品質チェックは既定 off です。辞書も空から始まり、使う人が指摘 → 承認して育てます。
  • 「範囲外ファイルの見張り (scope leash)」は今は警告のみです。強制的に止めるモードは、実績を見てから使う人が切り替えます。
  • Claude Code 本体のバージョンが上がると挙動が変わることがあります。CCH は追従を続けていますが、常に最新と一致する保証はありません。
