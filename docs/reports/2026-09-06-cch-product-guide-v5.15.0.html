CCH（Claude Code Harness）は、Claude Code や Codex（プログラムを書く AI）に追加する開発支援機能です。承認した計画を実行させると、プログラムの作成と動作確認を進め、確かめた結果と残った問題を返します。
頼み方と返る結果を見る導入して始める
初見の方、非専門家向け / 2026-09-06 / v5.15.0 の使い方
説明用の派生物。正本は README / spec。

計画を作る → 実装する（プログラムを書く）→ レビューする（別の担当が確かめる）→ リリースする（使える版を公開する）。公開は許可された範囲で進めます。

図の条件とコマンドを読む

計画は /harness-plan。人が範囲と完成条件を確認します。実装は /harness-work。担当が修正と検証を進めます。レビューは /harness-review。実装と分けて判定します。リリースは /harness-release。検査と承認の条件を満たした範囲で実行します。

指摘があれば修正へ戻します。修正上限に達しても合格しなければ未完了です。実行前の検査は実行時フロア 5 分類とガードレール R01〜R16。限定的な許可設定があり、適用範囲は利用アプリごとに異なります。

やさしく言うと
AI に作業を頼んでも、「次はこれをして」「動くか確認して」と細かく指示し続けると、管理する仕事が残ります。CCH は、その段取りを作業一覧と担当への指示に組み込みます。作る担当と確認する担当を分け、問題があれば修正へ戻します。利用者は「作りたいもの」と「使える状態になったか」の判断に集中できます。

たとえば、注文が二重に入る不具合なら

「注文ボタンを 2 回押すと、同じ注文が 2 件入る。1 件だけになるように直したい」。この依頼が、次のように進みます。

①
あなたが頼む
作りたい状態は「同じ注文は 1 件だけ」。まずは手元で修正と確認を進める、と範囲を決めます。
あなた: 出てきた計画が目的と合っているか確認する。
②
担当が調べて直す
不具合を再現し、原因を調べて修正します。必要な動作確認を行い、別の担当が変更内容を確かめます。
CCH: この段取りと完成条件を、担当へ引き継ぐ。
③
結果を見て判断する
何を直したか、1 件だけ保存されることをどう確認したか、まだ確かめていないことが返ります。
あなた: 条件を満たしたか、公開してよいかを判断する。

頼み方と報告内容の例です。この注文システムを実際に修正した結果ではありません。新しい機能の追加や、画面の改善にも同じ流れを使います。

同梱スキル（担当が読む作業手順）は、基本の 5 操作を含めて 23 個です。実行前の判定は Go というプログラミング言語で作られた単体の実行ファイルが行います。安全検査は実行時フロア 5 分類と、ガードレール R01〜R16 です。詳しい適用条件は安全の節にあります。

01 / Why

細かな指示を減らし、判断に使える結果を受け取る

CCH が減らすのは、作業のたびに段取りを組み直す手間です。何を作るか、結果を使ってよいかの判断は利用者に残します。

📋
完成の意味がぶれにくい
「直った」の意味を、そのつど確認する
「注文は 1 件だけ」のように、確かめられる完成条件を作業一覧へ残す
🛠
次の手を毎回指示しない
調査、修正、確認を順番に頼み直す
承認した範囲では、担当が必要な調査と修正を続ける
🔎
完了報告を判断しやすい
「できました」だけでは、使ってよいか決められない
確認した方法と結果、別の担当による指摘、未確認事項が返る
🔗
続きの説明を減らせる
担当や会話が替わるたびに、経緯を伝え直す
終わったこと、残った問題、次に試すことを引き継ぐ
02 / Quick start

小さな依頼を 1 つ渡して始める

Claude Code v2.1 以降が前提です。リポジトリ（開発ファイルをまとめて管理する場所）で claude を開き、次を 1 行ずつ実行します。対象のファイルへ書き込める環境を使います。

Claude Code
› /plugin marketplace add Chachamaru127/claude-code-harness
› /plugin install claude-code-harness@claude-code-harness-marketplace
› /harness-setup
# 最初の依頼
› /harness-plan 注文ボタンを 2 回押しても、同じ注文が 1 件だけ保存されるように直したい
# 到達点の目安: 仕様と作業一覧の下書きができる

上の依頼は、二重登録の不具合がある開発ファイルでの例です。仕様書 spec.md と作業一覧 Plans.md に計画が残ります。「同じ注文は 1 件だけ」という完成条件と、変更してよい範囲を確認します。承認した計画を /harness-work all で実行します。

Codex CLI / Cursor / Grok の導入と呼び方

リポジトリのルートで、Codex CLI は scripts/setup-codex.sh --user、Cursor は scripts/setup-cursor.sh、Grok は scripts/setup-grok.sh を実行します。Codex は更新後にセットアップを再実行し、再起動します。

Codex では $harness-plan、$harness-work all のようにスキルを指定します。プラグインが置かれていることと、専用担当が有効になっていることは別です。

marketplace の手順は配布版の導入入口です。Codex の更新手順と設定の扱いは Codex README を参照してください。

03 / The loop

まずは、計画を確認して実行を任せる

最初は「依頼する → 計画を確認する → 実行を任せる → 結果を見る」で始めます。下の 5 操作は、用途ごとの入口です。

実行中は担当が承認範囲で進めます。途中で新しい承認や重大な仕様判断が必要になったときに、利用者へ判断を返します。

📋
計画する
/harness-plan
依頼を仕様と作業一覧へ。範囲、完成条件、依存関係、停止条件を揃えます。
人がやること: 範囲と条件を承認するか、直す。
🛠
実装する
/harness-work
対象の件数に応じて、単独実行とチーム実行を選びます。必要なテストと修正を進めます。
任せること: 調査、修正、確認。新しい承認事項は本人へ返す。
🔎
レビューする
/harness-review
実装とは切り離して結果を確認します。重大な指摘が残っていれば完了できません。
受け取るもの: 指摘と確認結果。修正が必要か判断する根拠。
🔄
照合する
/harness-sync
計画と実装のずれを調べます。作業一覧の印だけで完成を判断しません。
必要なとき: 計画と実物が合っているか確かめたいとき。
📦
出荷する
/harness-release
検証済みの根拠を変更履歴、タグ、リリースへまとめます。リリース前検査を通します。
人がやること: 公開や本番反映の許可範囲を決める。
📍
現在地を見る
/harness-progress
補助操作です。作業一覧に記録された未着手、作業中、完了と判断待ちを確認します。
押さえる点: 完了率は件数比。完成条件の合格率ではありません。
対象の選び方、繰り返し実行、再開のコマンド

/harness-work 3 は作業番号 3 の指定です。件数指定ではありません。/harness-work all は承認済みの計画をまとめて実行します。

未指定時は 1 件で Solo（単独実行）、2〜3 件で Parallel（並行実行）、4 件以上で Breezing（担当を分ける実行）を選びます。明示した実行方法を優先します。

/harness-loop は繰り返し実行です。既定の上限は 8 サイクル。Claude Code では 1 回に 1 作業、Codex では実行可能な作業をまとめて進める経路があります。上限到達、対象終了、停滞、相談役の STOP、失敗、利用者の停止で終わります。

/harness-loop status で状態を確認し、/harness-loop stop で停止を要求します。/harness-work --resume latest は直近の実行の再開入口です。実行可能な作業がなくても、依存先待ちの未完了作業が残る場合があります。

04 / Safety layer

任せる範囲と、確認が必要な操作を分けておく

手元での修正と、公開中のシステムへの反映では影響が違います。CCH は、検査に接続された操作を実行前に調べます。適用範囲は利用するアプリによって異なります。

実行時フロア = 共通の判定規則
5 分類 / 一括無効化の設定なし
課金、外部送信、秘密ファイルの読み取り、本番反映、作業ツリーの外を壊す操作を分類して判定します。通信先や読取対象などの限定的な許可設定はあります。許可対象やリリース設定は利用者が管理します。
ガードレール = 操作ごとの判定規則
R01–R16 / 拒否、確認、警告
共有する主な版への直接送信（main への push）、保護ファイルの変更、共有履歴を上書きする送信（強制 push）、履歴の巻き戻しなどを判定します。規則の一部はプロジェクトに合わせて設定できます。
📋
既知の確認はまとめる
事前承認が使える操作は、計画時に対象範囲を確認します。承認には期限、対象作業、使用回数の上限があります。
✋
新しい承認は操作前に
作業中に新しい承認対象が見つかれば、その操作を止めます。独立して進められる作業は続けます。
🧾
止まった理由を残す
規則名、分類、判定結果を記録します。担当が自分の作業を通すために、利用者の保護設定を変更する運用にはしません。
05 / Current behavior

作る担当と、確かめる担当を分ける

注文の不具合を直す例では、全員に「同じ注文は 1 件だけ」という完成条件を渡します。実装した担当だけの判断で終わらせず、別の担当が変更と確認結果を見ます。

依頼から結果が返るまで。左から右へ進みます。
1
完成条件を固定
再現方法、変更範囲、合格条件を計画へ。
人: 範囲と完成条件を承認
2
実装担当へ渡す
依頼と根拠を渡し、担当ファイルを分ける。
実装担当: 修正と検証
3
指摘を修正へ返す
独立したレビューを行い、上限の範囲で直す。
レビュー担当: 実物を判定
4
根拠と残件を返す
条件ごとの結果、変更箇所、未確認事項を報告。
人: 受け入れや公開を判断
🛠
Worker = 実装担当
コードを調べ、原因を修正します。「注文は 1 件だけ」を確かめるために、必要なテストを行います。
🔎
Reviewer = レビュー担当
変更した実物と確認結果を、実装担当とは別に見ます。重大な問題が残っていれば、修正へ戻します。
🧭
Advisor = 相談役
難しい場面で呼ばれ、別の進め方や停止を助言します。成果物を合格にする最終判定は、レビュー担当に残します。
モデル名の全表、手動変更、レビュー担当の権限

モデルは、担当が使う AI の種類です。推論量（effort）は、考える処理に割り当てる量の設定です。以下は担当別の既定値で、利用者の明示指定を尊重します。

Claude の難しい判断と相談には Fable 5.1、実装と専用レビューには Sonnet 5 を使います。Codex のレビューや相談には GPT-6 astra、Breezing（複数の担当に分ける実行）の実装には GPT-5.6 luna を使います。

担当と経路モデル ID推論量
Claude の難しい判断 / 相談 / 一般レビュー用ルートclaude-fable-5-1high
Claude の実装担当claude-sonnet-5medium
Claude の専用レビュー担当claude-sonnet-5xhigh
Codex の標準処理 / 難しい判断 / レビュー / 相談gpt-6-astraxhigh
Codex Breezing の実装担当gpt-5.6-lunamax

これは親の会話のモデルを一律に固定する表ではありません。親の会話でモデルを変えても、子担当がすべて同じモデルに変わる設定ではありません。呼び出しで指定した値や、担当の設定をその経路で使います。Codex の ultra も明示指定として扱います。

Codex の native 子担当（Codex 自身が起動する担当）は、親の実行権限を継承します。モデルの担当設定だけで読み取り専用になるとは限りません。companion（別プロセスへの委譲）経由のレビューは、読み取り専用で実行します。

相談と修正が終わる条件

相談役の返答は PLAN（進め方）、CORRECTION（修正方針）、STOP（停止）の 3 種です。成果物の最終判定はレビュー担当に残します。

作業ごとのレビュー修正は既定で最大 3 回。Breezing 全体の統合レビューにも別の上限があります。上限に達して重大な指摘が残れば、完成扱いにせず、理由と判断材料を返します。

06 / Compare

手順を毎回頼むときと、CCH で回すとき

Claude Code や Codex でも、実装やテストは頼めます。CCH はそれらを共通の工程にまとめ、作業の引継ぎと完成の判定方法まで揃えます。

場面チャットで都度指示する運用CCH の既定運用
計画会話から範囲や条件を読み直す仕様と作業一覧に、完成条件と停止条件を残す
実装作業分割や担当の使い方を毎回伝える対象件数と依存関係を見て実行方法を選ぶ
確認実装の後に、必要な検証を追加で頼む作業で指定されたテストと独立したレビューを通す
引継ぎ前の会話を読み直してもらう完了事項、問題、検証結果、次に試すことを渡す
人の役割進め方と確認方法をその都度伝える作るもの、完成条件、許可範囲、追加判断に集中する

08 / Hosts

正式対応は CCH が定めた導入、起動、実行、リリースの検査を通した経路です。各アプリで使える機能や安全検査の範囲まで、同一という意味ではありません。

09 / FAQ

よくある質問

普通に AI に頼むのと、何が違う？

CCH は、依頼の整理、実装、動作確認、別の担当によるレビューを、繰り返し使える手順として追加します。毎回同じ段取りを頼み直す手間を減らせます。AI の間違いがなくなるわけではないため、残った指摘と未確認事項も返します。

途中で何度も確認される？

承認された範囲の可逆な作業は、担当が調べながら続けます。既知の確認事項は計画時にまとめます。新しい承認対象や重大な仕様判断が出た場合は、その操作の前に確認します。

コードを細かく読めなくても判断できる？

計画概要、進捗、受け入れの 3 画面で、条件と確認結果を見られます。たとえば「同じ注文が 1 件だけ保存されたか」の結果を確認します。自分の業務で使える状態かの判断や、新しい操作の許可は利用者に残ります。

進捗 100% なら、そのまま公開していい？

完成条件と公開条件を別に確認します。進捗の数値は Plans.md の完了件数 ÷ 全件数です。テスト合格率や本番確認の結果を表す数値ではありません。公開にはリリース前検査と許可範囲の確認が必要です。

ずっと自動で続けられる？

繰り返し実行の /harness-loop には、既定 8 サイクルの上限があります。停滞、相談役の停止判断、失敗、利用者の停止でも終わります。終了理由を見て、作業の完了と実行の停止を区別します。

10 / Glossary

言葉と、押さえること

プラグイン / スキル = アプリへの追加機能 / 担当が読む作業手順。
CCH を導入し、plan や work の手順を呼び出します。
spec.md / Plans.md = 仕様書 / 作業一覧。
正しい状態と、そこへ進む作業を分けて残します。
Worker / Reviewer / Advisor = 実装担当 / レビュー担当 / 相談役。
相談役の助言だけで、成果物を合格にはしません。
effort = モデルが考える処理に割り当てる量の設定。
high や xhigh などの値があります。利用者の明示指定を尊重します。
実行時フロア / ガードレール = 接続された操作を実行前に判定する 2 層。
フロアは 5 分類。ガードレールは R01〜R16。許可や適用範囲にも条件があります。
証拠 = 実行して得た確認記録。
テスト結果や再現手順の結果など。「担当が完了と言った」ことだけでは、未確認事項を埋められません。
最初に渡すもの
小さな依頼に「完成条件」と「変更してよい範囲」を添えて /harness-plan へ渡します。承認後に実行し、返ってきた結果と未確認事項で次の判断をします。
正直な但し書き
  • 担当モデルは v5.15.0 の既定値です。各モデルの性能順位や、実際の仕事での成功率を測定した結果ではありません。
  • 検査の適用範囲はホストと実行経路ごとに違います。接続されていない操作まで同じ検査を通るとは限りません。
  • 進捗画面の完了率は作業一覧の件数比です。Claude Code の画面ファイル再生成は編集やコマンド実行後に最大 60 秒に 1 回で、常時動く時計ではありません。
  • 同じリポジトリの担当間で情報を渡せますが、メッセージの内容検査は既定で無効です。相手の報告も検証対象として扱います。
  • モデルの提供状況、認証、利用上限、アプリ本体の変更は別の実行条件です。今回のガイド更新では、それらを新たに実機検証していません。
